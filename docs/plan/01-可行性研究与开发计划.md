# dsh-github-message：可行性研究与开发计划

> **2026-11-08 范围更新**：用户已确认三类消息（review / issue / @ 提醒），且 `dsh-github-message` 只负责推送；评审、分析、写回由 `dsh-my-superagent` 完成。核心改动以 [GitHub issue #1](https://github.com/xbzbing/dsh-my-superagent/issues/1) 的提案为准，本文件保留为可行性研究基线；当前开发计划见 [02-开发计划-三路提醒.md](02-开发计划-三路提醒.md)。

> 结论先行：**可行，但核心必须补上「GitHub 来源的确认、通知与动作」链路**。按当前代码，经 `sources.register` 注册的来源上报的信号，`system` 信任只会被准入为 `admitted`，`external` 信任只会被 `icode:` subject 的回源路径处理；**没有任何消费者把 `github:` subject 的信号变成给主人的提醒**。插件只负责推送；评审、Issue 分析、评论/写回由 `dsh-my-superagent` 完成。
>
> 2026-11-08 主人确认的范围是三类消息：**review（待我评审的 PR）、issue（维护项目的新 Issue）、AT（@ 我）**。核心改动提案已写入 [dsh-my-superagent issue #1](https://github.com/xbzbing/dsh-my-superagent/issues/1)；当前开发计划见 [02-开发计划-三路提醒.md](02-开发计划-三路提醒.md)。本文件保留为可行性研究基线，其中 review-only 的排期与验收已被 02 取代。

## 1. 任务理解与目标

### 1.1 任务理解

当前工作目录 `dsh-github-message` 是一个空仓库（仅 `.git`，remote 为 `git@github.com:xbzbing/dsh-github-message.git`）。结合「参考 dsh-icode-message 接入到 dsh-my-superagent」与参考文档、参考项目，本文按以下目标理解：

> 新建 `dsh-github-message` 插件，参考 `dsh-icode-message` 的「来源插件 + Web 面板」形态，把 GitHub 上「待我评审」的 PR 接成 `dsh-my-superagent` 的数据来源；先做提醒，评审任务作为后续阶段。

如果实际目标是「把 dsh-icode-message 整体并入核心」或「做 GitHub IM 桥」，本文的结论需要重做，见第 9 节待确认问题。

### 1.2 目标（v0.1）

1. 用本机已登录的 `gh` 只读轮询 GitHub，找出 `is:pr is:open review-requested:@me` 的 PR。
2. 按 `my-superagent/v1` 上报 `code-review.requested` 信号，字段稳定、可幂等去重。
3. 在 `dsh-my-superagent` 面板「来源」页可见，可开关；开启后经核心的注意力调度与 outbox 发到已绑定的 IM 桥。
4. 提供一个 Web 面板：GitHub 登录状态、检查周期、轮询/上报/去重/错误统计、核心信号落库情况。
5. 全程只读 GitHub；不评论、不打分、不合入、不改卡片。

### 1.3 非目标（v0.1）

- 不做 GitHub 自动评审，不写回评论/结论/打分。
- 不接 GitHub Webhook（本机没有稳定公网回调地址；参考项目也用轮询）。
- 不支持 GitHub Enterprise Server（先只支持 `github.com`）。
- 不做进程外 IM 桥、不改 `dsh-im-infoflow`。
- 不把 GitHub token 存进插件；复用 `gh` 的 keyring 登录态。

## 2. 现状核实

### 2.1 dsh-my-superagent（核心）

- 版本 `0.1.0`，最新提交 `0ad1c0b`（2026-11-07 21:26:59 +0800）。
- 关键文件与事实：

| 事实 | 位置 | 说明 |
| --- | --- | --- |
| 来源注册表只校验 `id`、`protocol`、`kinds`、`trust` | `src/host/registry.ts:215`、`src/protocol/providers.ts:63-68` | 没有 `notify` 能力；`trust` 取 `external` / `system` |
| `system` 信任免回源，准入直接 `admitted` | `src/host/admission/admission.ts:53-56` | `classifySignal`：`system → trusted-source` |
| `external` 未确认信号只有在 `subject` 能被回源识别时才交给回源 | `src/host/admission/admission.ts:107-112`、`src/host/sources/verification.ts:121-122` | `SourceVerifier.accepts` 只认 `icode:` subject |
| 只有回源确认路径会生成提醒 | `src/host/sources/verification.ts:255-273` | `notify()` 是 iCode/iCafe 专用文案与评审按钮 |
| 核心没有「已采纳信号 → 交付」的通用消费者 | `src/host/core.ts` 的 `wire()`、`src/host/events.ts` | 事件只有 `signal.accepted`，没有 `signal.admitted`；`SourceNotifier` 不存在 |
| 协议特性清单 | `src/protocol/messages.ts:37` | 当前 `['owner-images', 'owner-lookup']` |

**结论**：如果把 `dsh-github-message` 注册为：

- `trust: 'system'`：信号会 `admitted`，然后停在库里，**不会发通知**（当前没有任何消费者）。
- `trust: 'external'`：`subject` 不是 `icode:`，`accepts` 为 false，准入直接 `ignored`（`unverified-external`），**也不会发通知**。

这就是本任务唯一真正的阻塞点，也是 v0.1 必须动核心的原因。

### 2.4 参考文档与仓库的差异

Ku 文档《接入文档：把外部系统接成 dsh-my-superagent 的数据来源》（`TzLnX2etW6ekOe`）写于 2026-11-05，其中 4.4 节说：

> 经 `sources.register` 注册的来源，信号一律是 `external`……落库后停在 `new`，不会进入注意力调度，不会发通知；想触发提醒现阶段走 iCode/iCafe Webhook。

仓库在 2026-11-06 之后已经前进了两步：

1. ADR-0012：`SourceProvider` 可声明 `trust: 'system'`，准入直接 `admitted`。
2. ADR-0013：`external` 注册来源的 `icode:` subject 可由核心回源确认并提醒（dsh-icode-message 因此能工作）。

但**仍没有**「`system`/非 iCode subject 的已采纳信号 → 提醒」的通用消费者。文档的结论「外部来源不会提醒」对 GitHub 仍然成立，只是原因从「一律 external」变成了「没有消费者」。计划以仓库代码为准，并顺手在 ADR 里记录这个差异。

## 3. 可行性判断

### 3.1 分项结论

| 能力 | 可行性 | 说明 |
| --- | --- | --- |
| 用 `gh` 只读拉取「待我评审」PR | **可行** | 本机 `gh` 已登录；`search/issues` 实测可调；`review-requested:@me` 语义匹配 |
| 按协议上报信号 | **可行** | `sources.register` + `emit` 已稳定；dsh-icode-message 已跑通 |
| 信号落库、面板可见、来源开关 | **可行** | 核心已有来源页、开关、权限档位 |
| 信号变成 IM 提醒 | **当前不可行，需改核心** | 没有通用消费者；只改插件做不到 |
| 自动评审 GitHub PR | **高成本，不建议本期** | `Review` 聚合与 iCode 强耦合（见 3.2） |
| 接 GitHub Webhook | **不建议** | 本机无稳定公网入口；轮询足够 |

### 3.2 为什么「自动评审 GitHub PR」不是顺手的事

现有评审任务链路的前提是 iCode：

| 耦合点 | 位置 | GitHub 的差异 |
| --- | --- | --- |
| `reviews.patch_set INTEGER NOT NULL`，唯一键 `(subject, patch_set)` | `src/host/store/migrations.ts:272-292` | GitHub 没有数字补丁集，只有 head SHA；需要改列类型/迁移，或做本地版本映射 |
| `Review.repo` 按三段式厂内仓库校验 | `src/host/review/urls.ts:3-8`、`src/host/sources/cli.ts:20` | GitHub 是 `owner/repo` 两段 |
| 默认 prompt 明确写 iCode、`/icode` skill、打分 | `src/host/review/prompt.ts:6-16` | GitHub 要 `gh`/GitHub API，结论模型也不同 |
| 评审页 URL 固定 iCode 域名 | `src/host/review/urls.ts:2` | GitHub 是 `https://github.com/owner/repo/pull/n` |
| 通知/写回文案写死 iCode | `src/host/review/notices.ts`、`src/host/review/submit.ts:56` | 需要来源标签与写回目标 |
| 回源 CLI 白名单只有 `icode` / `icafe` | `src/host/sources/cli.ts:3-16` | 要么加 `gh` 白名单，要么走 provider 注册表 |
| 写回靠评审会话的 bash 调 `icode-cli` | `src/host/review/prompt.ts:36-48` | GitHub 要 `gh pr review` / REST review，且要防重复 |

因此 v0.2 有两条路：

- **A. 通用化评审聚合**：把 `patchSet` 改成字符串 revision、仓库/URL/prompt/写回按来源抽象，新增 `ReviewProvider` 注册表，插件实现 GitHub provider。干净，但要做迁移、面板、测试，约 5–8 天。
- **B. 核心内置 GitHub 适配**：像 `icode`/`icafe` 一样把 GitHub 写进核心。快一些，但违背「核心只处理语义、来源由插件接入」的架构，且 gh 凭据/白名单会进核心。

建议：**v0.1 先只做提醒**；等真实使用一段时间、确认 GitHub 评审请求的频率与价值后，再单独立项选 A/B。

### 3.3 方案对比

| 方案 | 内容 | 用户价值 | 成本（估） | 风险 | 结论 |
| --- | --- | --- | --- | --- | --- |
| A | 只做采集，不改核心 | 信号可查，无提醒 | 3–4 天 | 用户看不到提醒，插件像半成品 | 不推荐 |
| **B** | **采集 + 核心通用提醒** | **IM 收到「待我评审」+ 链接** | **6–9 天** | 核心改动需回归测试 | **推荐 v0.1** |
| C | B + GitHub 评审任务/写回 | 自动评审、评论、结论 | +5–8 天，含迁移 | schema/prompt/写回/权限 | v0.2 单独立项 |

## 4. v0.1 推荐方案

### 4.1 总体链路

```text
GitHub API  <--(gh api, read-only)--  dsh-github-message
                                          |
                                          | sources.register({ id:'github-message',
                                          |   trust:'system',
                                          |   kinds:['code-review.requested'],
                                          |   notify:{ 'code-review.requested':'action' } })
                                          v
                              dsh-my-superagent  SourceRegistry
                                          |
                                          v
                                   Intake.acceptSignal
                                          |
                                          v
                                   Admission (system -> admitted)
                                          |
                                          v
                             SourceNotifier（新增，通用）
                                          |
                                          v
                             AttentionScheduler -> Outbox -> IM Bridge
```

### 4.2 信号映射

`dsh-github-message` 每轮把每个「待我评审」的 PR 翻译成一条 `SignalDraft`：

```ts
{
  // 同一 PR 的同一 head SHA 只上报一次；head 变化才算新事实
  sourceEventId: `pr:${repo.toLowerCase()}#${number}:${headSha}`.slice(0, 256),

  kind: 'code-review.requested',

  // 事件发生时间；用 PR 的 updated_at，解析失败则跳过
  occurredAt: Date.parse(pull.updated_at),

  // 稳定对象标识；给未来核心按 subject 回源/评审用
  subject: `github:${repo}/pull/${number}`.slice(0, 512),

  // 一行摘要；换行压成空格，控制字符去掉
  summary: `${repo} #${number} ${title}`.slice(0, 2000),

  // PR 作者；GitHub 搜索不提供「谁点的请求评审」，不要伪造 requestedBy
  actor: { id: pull.user.login },

  links: [{ title: `GitHub #${number}`, url: pull.html_url }],

  payload: {
    repo, number, title, author, headSha,
    baseRef, draft, updatedAt, url,
    // 明确标记这是 review-requested 搜索的结果
    via: 'review-requested',
  },
}
```

约束：

| 字段 | 约束 | 做法 |
| --- | --- | --- |
| `sourceEventId` | 1–256 | `pr:<repo>#<n>:<sha>`；repo 小写归一化 |
| `subject` | 1–512 | `github:owner/repo/pull/<n>`；两段仓库名，保留大小写用于展示 |
| `summary` | ≤2000 | 单行、去控制字符、截断 |
| `payload` | ≤64 KB | 只放白名单字段；不放 raw API 响应、diff、token |
| `links` | ≤20，http(s)，≤2048 | 只放 PR 页面；由核心 Schema 校验 |

去重：

1. **同一 head SHA**：`sourceEventId` 相同，核心 `(source, source_event_id)` 唯一约束吸收。
2. **本地 `seen.json`**：核心对停在 `new` 的信号 7 天后清理；插件持久化已上报键，重启不重报。
3. **本轮内 Set**：搜索分页/多个查询重复返回同一 PR 时只报一次。
4. **不要**把轮询时间拼进键；否则每轮都是新记录。

### 4.3 核心改动（dsh-my-superagent）

#### 4.3.1 协议

```ts
// src/protocol/providers.ts
export type SourceNotify = Readonly<Record<string, 'action' | 'result'>>;

export interface SourceProvider {
  id: string;
  protocol: readonly string[];
  kinds: readonly string[];
  trust?: SourceTrust;
  // 新增：kind -> 提醒意图；只对 trust='system' 的来源生效
  notify?: SourceNotify;
}
```

`src/protocol/messages.ts` 的 `PROTOCOL_FEATURES` 增加 `'source-notify'`。这是同主版本的可选能力，不需要升协议版本。

#### 4.3.2 注册表

- `SourceRegistry.register` 校验 `notify`：
  - 必须是普通对象；
  - 每个 key 必须出现在 `kinds` 里；
  - 每个 value 只能是 `'action' | 'result'`；
  - 最多 20 个键。
- `RegisteredSource` 增加 `readonly notify?: SourceNotify`。
- `sources.list` RPC 回传 `notify`（可选；面板可显示「会提醒」）。

#### 4.3.3 准入事件

`CoreEvents` 增加：

```ts
'signal.admitted': { id: string; source: string; kind: string; trust: Trust };
```

`Admission.apply` 在 `settle` 实际推进到 `admitted` 后发出事件（`ignored` 不发）。重复上报时 `settle` 返回 0，不发事件，保持幂等。

#### 4.3.4 `SourceNotifier`（新增 `src/host/sources/notifier.ts`）

职责：把「`trust='system'`、来源声明了 `notify[kind]`、已 `admitted`、还没通知过」的信号转成一条 `DeliveryRequest`。

```ts
interface SourceNotifierDeps {
  signals: SignalStore;
  sources: SourceRegistry;
  events: EventBus<CoreEvents>;
  clock: Clock;
  deliver(request: DeliveryRequest, origin: Origin): string | undefined;
  logger?: Logger;
}

class SourceNotifier {
  start(): () => void;        // 订阅 signal.admitted / source.activated；启动时补扫
  recover(source: string): void; // 已 admitted 但 notice_key 为空的信号
  stop(): void;
}
```

行为：

1. 只处理 `signal.trust === 'system'`（`external` 的已确认信号仍由 `SourceVerifier` 负责，避免两套通知重复）。
2. `sources.lookup(source)?.notify?.[kind]` 取意图；取不到、来源未注册/未开启则跳过。
3. 读取完整信号；若 `notice_key` 已存在则跳过。
4. 先 `signals.markNotified(id, 'source:'+id)`，再 `deliver`；投递失败只记日志，启动/激活时补扫未标记的信号。
5. 渲染：
   - `intent` = 配置的 `action` / `result`；
   - `title` = 摘要第一行，转义 Markdown，截 200；
   - `body` = 摘要 + 来源/actor + 最多 3 条链接；
   - `refs` = `[{ kind: 'signal', id }]`；
   - `dedupeKey` = `source-signal:<id>`；
   - 不设 `immediate`：让免打扰、每小时 action 上限、摘要规则照常生效。
6. `start()` 时对当前所有已开启的 `notify` 来源补扫；`source.activated` 时补扫该来源。

`SignalStore` 增加：

```ts
noticeKey(id: string): string | undefined;          // 读现有 notice_key
markNotified(id: string, key: string): number;      // UPDATE ... WHERE id=? AND notice_key IS NULL AND state='admitted'
unnotified(source: string, limit: number): Signal[];// state='admitted' AND notice_key IS NULL
```

`notice_key` 列已存在（迁移 v9），**不需要新迁移**。

#### 4.4.2 轮询算法

```text
pollOnce():
  now = clock.now()
  since = now - windowMs
  seenThisPoll = Set()

  page = 1
  results = []
  while page <= maxPages:
    resp = gh.searchIssues(query, page)     // is:pr is:open review-requested:@me
    results += resp.items
    if resp.items.length < 100: break
    page += 1

  for item in results (最多 maxResults):
    repo = parse repository_url
    if !item.pull_request: skip
    if item.state !== 'open': skip
    updatedAt = Date.parse(item.updated_at)
    if !finite(updatedAt) || (windowMs > 0 && updatedAt < since): filtered++
    if !includeDrafts && item.draft: filtered++

    detail = gh.pull(repo, item.number)     // 缓存 (repo, number, updated_at) -> head.sha
    if detail.state !== 'open' || detail.merged: filtered++
    headSha = detail.head.sha
    if !/^[0-9a-f]{40}$/: skipped++

    id = `pr:${repo.toLowerCase()}#${number}:${headSha}`
    if seenThisPoll.has(id) || seen.has(id, now): duplicates++
    result = emit(draft)
    if !result.accepted: errors++ (source-disabled 等，下轮重试)
    else: seen.add(id, now); emitted++ 或 duplicates++
```

关键约束：

- **只读** `gh api`：`user`、`search/issues`、`repos/{owner}/{repo}/pulls/{n}`、`auth status`。不调 `gh pr review`、`gh pr comment`、`gh api -X POST/PATCH/PUT/DELETE`。
- `gh` 失败分类：`auth`（401/未登录）、`rate-limit`（403/429 + `rate limit`/`X-RateLimit-Remaining: 0`）、`not-found`（404）、`network`（超时/DNS）、`other`。
- 限流：搜索 30 次/分钟；默认 5 分钟一轮，一轮 1 次搜索 + N 次详情（N ≤ maxResults）。详情按 `(repo, number, updated_at)` 缓存；一轮最多 `maxResults` 次。
- 失败退避：连续失败 1/2/4/8… 最多 30 分钟；限流则按 `X-RateLimit-Reset` 等到重置后再试。
- 不重叠：上一轮未结束时跳过本轮。
- 单个 PR 详情失败不阻断整轮；记错误，下一轮重试。

#### 4.4.3 `gh` 封装

```ts
interface GhResult { ok: true; json: unknown; headers?: Record<string, string> }
                 | { ok: false; kind: 'auth' | 'rate-limit' | 'not-found' | 'network' | 'other'; detail: string; resetAt?: number }

interface GhRunner {
  available(): boolean;
  authStatus(): Promise<AuthStatus>;
  api(path: string, options?: { include?: boolean; paginate?: boolean }): Promise<GhResult>;
}
```

- `spawn('gh', ['api', path, ...])`，`shell: false`，`detached: true`（超时杀进程组），`stdio: ['ignore','pipe','pipe']`。
- 最小环境：`HOME`、`PATH`、`LANG`、`LC_ALL`、`HTTP(S)_PROXY`、`NO_PROXY`、`GH_CONFIG_DIR`、`XDG_CONFIG_HOME`；`GH_PROMPT_DISABLED=1`。
- 不传 `GH_TOKEN`/`GITHUB_TOKEN`，避免插件读到别的 token；用户要换账号用 `gh auth switch`。
- 输出上限 4 MB；超时 20 秒；`--include` 时按第一个空行拆 headers/body。
- `gh` 在 HTTP 304 时退出码非 0；通知模式要把它当「未变化」，不是错误。v0.1 搜索暂不需要 304。

#### 4.4.4 登录状态

| 状态 | 来源 | 面板文案 |
| --- | --- | --- |
| `ok` | `gh auth status --hostname github.com` 解析到账号 + `gh api user` 成功 | 已登录：`xbzbing` |
| `unauthenticated` | 输出包含 `You are not logged into any GitHub hosts` / `not logged in` | 未登录，请 `gh auth login` |
| `expired` | API 返回 401 / `Bad credentials` | 凭据失效，请重新登录 |
| `missing` | `gh` 不存在 | 未安装 gh |
| `unknown` | 其他 | 未知 |

面板显示 token scopes；如果以后接通知模式，提示需要 `notifications` scope（`gh auth refresh -s notifications`）。

### 4.5 安全边界

| 边界 | 做法 |
| --- | --- |
| GitHub 只读 | 只允许 `gh api` GET 类路径；代码里不出现 `-X POST/PATCH/PUT/DELETE`、`gh pr review`、`gh pr comment` |

### 4.6 验收标准（v0.1）

1. 安装两个插件后，超级助理「来源」页出现 `github-message`，显示 `系统信任`，开关默认关闭。
2. 开启来源；用 fake gh 或真实账号制造一个 `review-requested:@me` 的 PR；一轮内 `signals` 表出现：
   - `source='github-message'`
   - `kind='code-review.requested'`
   - `subject='github:owner/repo/pull/<n>'`
   - `state='admitted'`，`notice_key` 非空
3. 已绑定 IM 桥时，收到一条 action 提醒：标题含 `owner/repo #n <title>`，正文含 GitHub 链接，refs 指向该信号。
4. 同一 head SHA 再轮询/重启：不重复提醒；`emit` 返回 `duplicate: true` 或本地 seen 命中。
5. PR 推新 commit（head SHA 变化）：再收到一条提醒。
6. PR 关闭/合并/已评审：不再收到新提醒。
7. 来源关闭：不发提醒；重新开启后，当前仍待评审的 PR 会补上。
8. 面板：登录状态、周期保存、统计、最近错误、核心信号计数都正确。
9. `dsh-my-superagent` 的 `npm run check` 与 `dsh-github-message` 的 `npm run check` 全绿；核心现有 iCode 路径回归测试全绿。
10. 全程没有对 GitHub 的写请求。

## 5. 第二阶段：GitHub 评审任务（v0.2，单独立项）

### 5.1 目标

在 v0.1 的提醒卡上增加「开始评审」，复用现有评审任务的状态机、并发、超时、会话收紧与结论回传，把 GitHub PR 的 diff 准备成材料，评审会话读材料后给出结论；权限档位为放宽档时，把评论/结论写回 GitHub。

### 5.2 必须先解决的模型问题

| 问题 | 现状 | 建议 |
| --- | --- | --- |
| 补丁集 | `reviews.patch_set INTEGER`，唯一键 `(subject, patch_set)` | 把 `patch_set` 改成文本 `revision`（head SHA），或新增 `revision TEXT` 并迁移；面板/通知显示短 SHA |
| 仓库名 | 三段式 iCode 仓库 | 引入 `SourceRef`/`repo` 通用字符串；URL 按来源生成 |
| prompt | 默认 iCode 专用 | 按来源提供默认模板；`{repo}/{change}/{patchSet}/{title}/{materials}` 保留，新增 `{source}`/`{url}` |
| 写回 | 评审会话用 bash 调 `icode-cli` | 由核心/提供方执行 `gh api` 提交 review；禁止模型直接写，或至少用 provider 的统一入口 |
| 评审页 | iCode 固定域名 | 来源在信号 `links` 里给 URL，核心校验后采用（ADR-0025 已有类似机制） |
| 权限 | 来源档位已存在 | 复用 `read-only/auto/workspace-write`；GitHub 写回只允许放宽档 |

### 5.3 推荐架构

新增一个可选的 **评审提供方注册表**，与 `sources` / `bridges` 并列：

```ts
interface ReviewProvider {
  source: string;                       // 必须对应一个已注册来源
  protocol: readonly string[];          // ['my-superagent/v1']
  accepts(subject: string): boolean;    // 例如 github:owner/repo/pull/<n>
  snapshot(input: { subject: string; owner: string }): Promise<Fetched<ReviewSnapshot>>;
  changedFiles(input: { subject: string; revision: string }): Promise<Fetched<ChangedFile[]>>;
  diff(input: { subject: string; revision: string; path: string }): Promise<Fetched<FileDiff>>;
  submit?(input: { subject: string; result: ReviewResult; permission: SourcePermission }): Promise<Fetched<void>>;
}
```

`dsh-github-message` 实现 GitHub provider（`gh` 只读 + `gh api` 写回），核心只依赖接口。这样：

- 核心不认识 GitHub；
- iCode/iCafe 继续走内置适配；
- 以后接 GitLab/Gitee 只加插件。

代价：协议扩展、迁移、`ReviewService` 改造、面板与测试，约 5–8 天；建议在 v0.1 使用 2–4 周后再决定。

### 5.4 写回安全

- 只允许 `POST /repos/{owner}/{repo}/pulls/{n}/reviews` 一次提交（body + event + comments）；请求体带 HTML marker/幂等键，重试不重复。
- 评论路径/行号来自评审结果，必须校验属于本次 PR 的改动文件；不合法就降级为总评。
- 禁合入、禁推送、禁改他人 PR、禁打分（GitHub 没有 iCode 式分数，`score` 可映射到 review event 或不使用）。
- 写回前再次用 GitHub API 确认 PR 开着、head SHA 与评审时一致；不一致按 `superseded` 结束。

## 8. 风险与应对

| 风险 | 影响 | 概率 | 应对 |
| --- | --- | --- | --- |
| 核心没有通用提醒消费者 | GitHub 信号不提醒 | **确定** | M1 先做 `SourceNotifier`；不接受改核心则 v0.1 降级为采集 |
| 改核心引入回归 | 现有 iCode/IM 行为变化 | 中 | `notify` 默认无；只对 `system` 生效；契约测试 + 五轴评审 |
| GitHub 搜索限流/滥用 | 轮询失败、提醒延迟 | 中 | 默认 5 分钟；`maxResults`/缓存；`X-RateLimit-Reset` 退避；面板显示 |
| gh 未安装/未登录/SSO | 无数据 | 中 | 登录面板、错误分类、README；SSO 提示 `gh auth refresh` |
| `review-requested` 语义遗漏 | 漏提醒（如已评审后重新请求） | 中 | v0.1.1 加 notifications 模式；文档说明 |
| 首装刷屏 | 打扰主人 | 中 | 来源默认关闭；window 7 天；maxResults；先看面板再开启 |
| 详情调用放大 | 大仓库/多 PR 时限流 | 中 | 缓存 `(repo,number,updated_at)`；并发 4；上限 100 |
| 外部内容注入 | 提示注入/格式破坏 | 低 | 只读、单行摘要、控制字符过滤、核心转义、链接白名单 |
| 二期 schema 返工 | 评审任务延期 | 高 | 一期不承诺评审；二期单独立项、先 ADR/迁移 |
| 两插件版本不一致 | 静默不提醒 | 中 | `protocol.features` 检查 `source-notify`；面板明示；README 写最低版本 |

## 9. 待确认问题

1. **范围**：v0.1 先只做「待我评审」的 PR，还是同时接全部 GitHub 通知（mention/assign/comment/ci/state_change）？建议先 review-only，通知放 v0.1.1。
2. **核心改动**：是否接受在 `dsh-my-superagent` 增加 `SourceNotifier`（约 1.5–2 天）？如果不接受，v0.1 只能做到「采集 + 面板可见」，没有 IM 提醒。
3. **默认窗口**：7 天是否合适？GitHub 的待评审 PR 可能停留更久；可改 14/30 天或 `0`（不过滤）。
4. **评审任务**：现在就要 v0.2（自动评审 + 写回），还是先交付 v0.1 看使用频率？
5. **GitHub 范围**：只支持 `github.com`，还是也要 GitHub Enterprise Server？
6. **面板语言**：默认中文 + 英文 locale（与 dsh-icode-message 一致），还是只做中文？
