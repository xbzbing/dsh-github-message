## 1. 已确认的决定

| 决定 | 内容 |
| --- | --- |
| 消息范围 | 三类：待我评审的 PR（review）、我维护项目的新 Issue（issue）、@ 我或我所在团队的消息（AT/mention） |
| Issue 提醒 | 提醒主人「是否进行分析」，由主人决定是否开始 |
| 职责边界 | `dsh-github-message` **只负责消息推送**（轮询 GitHub → 上报信号）；评审、Issue 分析、评论/写回全部由 `dsh-my-superagent` 完成 |
| 核心改动 | **不直接修改** `dsh-my-superagent`；改动方案已写成 [issue #1](https://github.com/xbzbing/dsh-my-superagent/issues/1)，由 superagent 项目自行实现 |
| 信任级别 | 插件以 `trust: 'external'` 注册，核心回源确认后才采纳；插件不冒充 `system` |
| GitHub 访问 | 只读；复用本机 `gh` keyring，不保存 token，不调用任何 GitHub 写接口 |

## 2. 总体架构

```text
GitHub（私有/公开仓库）
        │  gh api GET / search / notifications
        ▼
dsh-github-message（本仓库）
  ├─ review 流：search review-requested:@me
  ├─ issue 流：维护仓库列表 + search is:issue created:>=
  └─ mention 流：notifications(reason=mention/team_mention) 或 search mentions:@me
        │  sources.register(id='github-message', trust='external',
        │                  kinds=[code-review.requested, github.issue.opened, github.mention])
        │  emit(SignalDraft)
        ▼
dsh-my-superagent（另一个项目，按 issue #1 实现）
  回源确认 → 通知/动作路由 → 评审任务 / Issue 分析任务 / @ 提醒
        │
        ▼
     IM 桥（dsh-im-infoflow 等）
```

插件与核心的依赖关系：

- 插件可以先完成、先安装；旧核心未支持 `github:` subject 时，信号会被记为 `ignored`（不会误提醒）。当前核心 P1 已支持。
- 插件在注册时读取 `mySuperagent.protocol.features`；核心 P1 已增加 `github-source`，旧核心缺失时面板提示升级并保持 dry-run。
- 来源默认关闭；在超级助理的「来源」页打开后，下一轮自动补齐。

## 3. 插件职责与三路数据流

### 3.1 review 流（待我评审）

- 查询：`is:pr is:open review-requested:@me`，`sort=updated&order=desc`，`per_page=100`。
- 每条结果补一次 PR 详情（`GET /repos/{owner}/{repo}/pulls/{n}`）取 `head.sha`、`state`、`merged`、`base.ref`、`draft`。
- 过滤：`state=open`、未合并、`head.sha` 为 40 位十六进制、`updated_at` 在窗口内（默认 7 天）。
- 事件键：`review:<owner>/<repo>#<n>:<headSha>`。
- 信号：`kind='code-review.requested'`，`subject='github:<owner>/<repo>/pull/<n>'`。
- 去重：同一 head SHA 只报一次；PR 推新 commit（head 变化）再报。

### 3.2 issue 流（维护项目的新 Issue）

- 配置 `repos`：主人维护的仓库列表，`owner/repo`，默认空；面板可编辑。
- 每个仓库查询：`repo:<owner>/<repo> is:issue is:open created:>=<since>`，`sort=created&order=desc`，`per_page=50`。
- `since` = 上次成功轮询时间 - 10 分钟重叠；首轮 = 当前时间 - `windowMs`（默认 7 天）。
- 过滤：不是 PR（结果无 `pull_request`）、`state=open`、`created_at` 有效。
- 事件键：`issue:<owner>/<repo>#<n>`；同一 Issue 只报一次（编辑/评论不重复）。
- 信号：`kind='github.issue.opened'`，`subject='github:<owner>/<repo>/issues/<n>'`。
- 仓库数量上限 `maxRepos`（默认 10）；每个仓库一次搜索，5 分钟一轮约 2 次/分钟，低于 30 次/分钟的搜索限流。

### 3.3 mention 流（@ 我）

优先用 Notifications API：

- `GET /notifications?all=true&per_page=50&since=<cursor>`；`reason` 取 `mention`、`team_mention`。
- 只处理 `subject.type` 为 `Issue` 或 `PullRequest` 的通知；`Discussion`、`Commit` 等先跳过并计 filtered。
- 对每条通知：
  - `subject.latest_comment_url` 存在 → 读取该评论，取 `id`、`body`、`user.login`、`html_url`、`created_at/updated_at`；
  - 没有评论 URL（例如 Issue 正文 @）→ 读取 `subject.url` 对应的 Issue/PR 正文；
  - 摘要取正文中包含 `@login` 的片段，截 300–500 字；没有找到 @ 文本则跳过（避免把普通通知当 AT）。
- 事件键：`mention:<owner>/<repo>#<n>:<commentId>`；没有 commentId 时用固定的 `body`。
- 信号：`kind='github.mention'`，`subject='github:<owner>/<repo>/issues/<n>'`（PR 也用 issues 数字，payload 标 `isPull`）。
- 认证：Notifications API 对私有仓库接受 `repo` scope；公开仓库可能需要 `notifications` scope。插件检测 `gh auth status` 的 scopes，缺失时：
  - 面板提示 `gh auth refresh -s notifications`；
  - 或降级为 `mentions:@me` 搜索（`is:issue is:open mentions:@me`），按 Issue 级别去重，精度较低。
- 游标：`since` 持久化；首轮 `now - windowMs`；收到 304 视为未变化；`X-Poll-Interval` 大于配置间隔时以 GitHub 为准。
- 失败重试：单条评论读取失败记错误，不推进该条游标；下一轮重试；连续失败按退避。

### 3.4 轮询编排

```text
pollOnce():
  review = try(reviewStream())      // 1 次 search + N 次 detail
  issue  = try(issueStream())       // maxRepos 次 search
  mention= try(mentionStream())     // 1 次 notifications + M 次 detail
  汇总统计；单个流失败不影响其他流
```

约束：

- 上一轮未结束跳过本轮。
- 每个流独立统计 fetched/emitted/duplicates/filtered/errors。
- `emit` 返回 `accepted:false`（`source-disabled` 等）时不写 seen，下一轮重试。
- `emit` 返回 `duplicate:true` 时写 seen 并计 duplicate，不重复提醒。
- 速率：review 1 + issue ≤10 + mention 1（+评论详情 ≤10）≈ 每轮 ≤22 次请求；5 分钟一轮，远低于 5000/小时与 30/分钟搜索限制；如配置更多仓库，按 `maxRepos` 截断并提示。

## 4. 信号字段

| 字段 | review | issue | mention |
| --- | --- | --- | --- |
| `kind` | `code-review.requested` | `github.issue.opened` | `github.mention` |
| `sourceEventId` | `review:<repo>#<n>:<headSha>` | `issue:<repo>#<n>` | `mention:<repo>#<n>:<commentId|body>` |
| `subject` | `github:<repo>/pull/<n>` | `github:<repo>/issues/<n>` | `github:<repo>/issues/<n>` |
| `occurredAt` | PR `updated_at` | Issue `created_at` | 评论/正文 `updated_at` |
| `summary` | `<repo> #<n> <title>` | `新 Issue：<repo> #<n> <title>` | `<repo> #<n> 有人 @ 你` |
| `actor` | PR 作者 | Issue 作者 | 评论作者 |
| `links` | PR 页面 | Issue 页面 | 评论/Issue 页面 |
| `payload` | repo/number/title/author/headSha/baseRef/draft/updatedAt/url/via | repo/number/title/author/labels/state/createdAt/url/via | repo/number/title/commentId/author/excerpt/url/via/isPull |

约束：

- `sourceEventId` ≤256；`subject` ≤512；`summary` ≤2000；`payload` ≤64 KB；`links` ≤20。
- 所有来自 GitHub 的文本：去控制字符、换行压成空格、按字段截断；不把 HTML/脚本带进 Markdown。
- 不放 raw API 响应、diff、token、邮箱等无关字段。
- `repo` 在事件键中小写归一化，展示保留原大小写。

## 5. 配置

```yaml
# cordis.patch.yml
- insert:
    - id: dsh-github-message
      name: dsh-github-message
      config:
        intervalMs: 300000
        repos:
          - xbzbing/dsh-git-panel
          - xbzbing/dsh-my-superagent
```

| 键 | 默认值 | 说明 |
| --- | --- | --- |
| `intervalMs` | `300000`（5 分钟） | 轮询间隔；最小 60 秒，最大 24 小时。实际间隔取本值与 GitHub `X-Poll-Interval` 的较大者 |
| `windowMs` | `604800000`（7 天） | review/issue/mention 首轮与过滤窗口；`0` 表示不过滤 |
| `repos` | `[]` | 维护中的仓库列表，`owner/repo`；issue 流必填 |
| `maxRepos` | `10` | 单轮最多查多少个仓库 |
| `maxResults` | `100` | review/issue 单流单轮最多处理多少条 |
| `maxPages` | `3` | 每个搜索最多翻几页 |
| `includeDrafts` | `true` | 是否提醒 draft PR |
| `mentionMode` | `notifications` | `notifications` / `search` / `off` |
| `timeoutMs` | `20000` | 单次 `gh` 调用超时 |
| `cliPath` | `gh`（PATH） | 可用 `DSH_GITHUB_CLI` 覆盖 |
| `onStart` | `true` | 加载后立即轮询一次 |
| `stateFile` | `$DSH_HOME/dsh-github-message/seen.json` | 去重；`false` 只在内存 |
| `seenTtlMs` | `7776000000`（90 天） | 去重记录保留期 |
| `seenMaxEntries` | `20000` | 去重记录上限 |
| `logFile` | `$DSH_HOME/dsh-github-message/poll.log` | 每轮摘要；`false` 关闭 |
| `statsFile` | `$DSH_HOME/dsh-github-message/stats.json` | 累计统计 |
| `runtimeConfigFile` | `$DSH_HOME/dsh-github-message/config.json` | 面板保存的周期与仓库列表 |

面板保存的 `intervalMs`/`repos` 写入 `$DSH_HOME/dsh-github-message/config.json`，优先于 Cordis patch；保存后立即重排定时器。实际等待时间为 `max(intervalMs, X-Poll-Interval)`；GitHub 的间隔在失败退避期间也会保留。

## 7. 面板

复用三个槽位：`settings.section`（完整设置页）、`plugins.bundle.config`（插件页配置卡）与
`shell.overlay`（右下角本地提示浮层，见 ADR-0005）。

内容：

1. **GitHub 登录**：`gh auth status` 的账号、token scopes、API 探测（`gh api user`）、检查登录按钮；未登录/失效/缺 `notifications` scope 的提示。
2. **核心能力**：`mySuperagent.protocol.features` 是否含 `github-source`；来源是否注册；核心是否已支持 `github:` subject。当前核心 P1 已支持；旧核心缺失时提示升级并保持 dry-run；完全没有核心时显示「未接入超级助理」，消息改走右下角提示。
3. **仓库列表**：多行文本，每行 `owner/repo`；保存时校验格式、去重、上限 `maxRepos`。
4. **检查周期**：当前周期、下一轮时间、按分钟修改并保存。
5. **三路统计**：review/issue/mention 各自的 fetched/emitted/duplicates/filtered/errors；最近 5 轮表；最近错误。
6. **核心信号**：只读 `$DSH_HOME/dsh-my-superagent/state.sqlite`，按 `source='github-message'` 与 kind 统计 `new/admitted/ignored/digested`；读不到降级。
7. **本地提示**：未接入核心时，采集到的新事实在右下角弹卡片；每条只弹一次，记录写 `notified.json` 而不写 `seen`；已接入核心时静默。
8. **操作**：立即检查、重置统计、检查登录。

## 8. 错误处理与限流

| 场景 | 行为 |
| --- | --- |
| `gh` 未安装 | 面板「未安装」；轮询不启动；README 写安装方式 |
| 未登录 / 401 | `login.api='expired'`；暂停轮询；面板提示 `gh auth login` |
| 缺 `notifications` scope | mention 流降级为 search 或标记不可用；面板提示 `gh auth refresh -s notifications` |
| 403/429 限流 | 读 `X-RateLimit-Remaining/Reset`；等到重置；指数退避；不标记 seen |
| 404 | 单条跳过（PR/Issue/评论被删）；计 filtered，不刷错误 |
| 网络/超时 | 指数退避 1/2/4/8… 最多 30 分钟；下一轮重试 |
| 输出不是 JSON | 记错误，不中断其他流；下一轮自愈 |
| `source-disabled` | 不写 seen；面板提示去超级助理来源页开启；下一轮重试 |
| `duplicate:true` | 写 seen，计 duplicate；不重复提醒 |
| 单条坏记录 | 跳过并计 skipped；不因一条坏数据中断整轮 |

## 9. 安全

- **只读**：只允许 `gh api` GET/search；代码中不出现 `-X POST/PATCH/PUT/DELETE`、`gh pr review`、`gh pr comment`。
- **参数**：仓库名 `^[A-Za-z0-9_.-]+/[A-Za-z0-9_.-]+$`；PR/Issue 编号正整数；SHA 40 位十六进制；路径/URL 逐项校验。
- **凭据**：不读 token、不存 token、不写日志；`gh` 用 keyring；最小环境不传 `GH_TOKEN`/`GITHUB_TOKEN`。
- **外部内容**：summary/excerpt 去控制字符、单行、截断；核心渲染时转义 Markdown；链接只接受 `https://github.com/...`。
- **刷屏**：来源默认关闭；核心 action 每小时上限、免打扰、摘要规则照常；插件 `maxResults`/`maxRepos`/window 限流。
- **卸载**：`scope.effect` 清理定时器、来源句柄、状态落盘。

## 12. 验收标准

1. 安装后，「来源」页出现 `github-message`，`外部信任`，默认关闭；面板显示 GitHub 登录与核心能力状态。
2. 开启后，三类信号都能落库：
   - `code-review.requested`，`subject='github:<repo>/pull/<n>'`
   - `github.issue.opened`，`subject='github:<repo>/issues/<n>'`
   - `github.mention`，payload 含评论 id 与摘要
3. 核心 P1 后，IM 先收到三类纯文本提醒；P2/P3 再为 review/issue 加「开始/忽略」与任务，mention 带链接与摘要。
4. 同一事实不重复：同一 head SHA、同一 Issue、同一条评论各只提醒一次；重启/重装后仍不重复。
5. 新 commit / 新 Issue / 新评论能产生新提醒。
6. PR 关闭、Issue 关闭、评论删除后不再提醒。
7. 来源关闭时不提醒；重新开启后能补齐当前仍符合条件的 review/issue/mention。
8. `gh` 未登录/限流/网络失败时，面板可见原因并退避；不影响其他流。
9. `npm run typecheck`、`npm test`、`npm run build` 全绿；e2e 不写真实 GitHub。
10. 面板中英文、README、安装/卸载/更新步骤可用。

## 13. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 旧核心不支持 GitHub 来源 | 插件只能采集，不能提醒 | 核心 P1 已完成；旧核心升级后重新加载插件；面板提示 |
| 仓库列表过多 | 搜索限流/延迟 | `maxRepos` 默认 10；每仓库一次搜索；5 分钟一轮；面板提示 |
| Notifications scope 不足 | mention 流不可用 | 面板提示 `gh auth refresh -s notifications`；降级 `mentions:@me` |
| 评论级 @ 漏报 | 提醒不全 | notifications 为主；search 为降级；文档说明 |
| 团队 @ 校验复杂 | 误报/漏报 | 核心按团队成员校验；查不到降级为「团队被 @」并在正文说明 |
| Issue 分析工作区/权限不清 | 分析会话建错地方 | 核心 issue #1 开放问题；先沿用 review workspace 或新增 analysis workspace |
| 评审写回重复/越权 | 重复评论/误操作 | 核心 issue #1 要求幂等 marker、权限档位、禁合入/推送 |
| 首装刷屏 | 打扰 | 来源默认关闭；window 7 天；maxResults/maxRepos；先看面板再开启 |
| 外部内容注入 | 提示注入 | 只读、转义、外部数据标记；核心 prompt 约束 |
