# ADR-0004：三路独立轮询、时间窗与退避

review、issue、mention 三个流在同一轮中顺序执行，但各自捕获错误、各自统计；一个流失败不影响另外两个。

## 背景

三类查询的速率限制与失败模式不同：search 30 次/分钟、Notifications 5000 次/小时。Issue 流按维护仓库数量放大请求数，单个仓库 404 不应拖垮 review。首次安装又容易把很久以前的待办一次性刷出来。

## 决策

- 每轮顺序执行 review → issue → mention；每个流独立 `try/catch`，错误写进该流摘要。
- review 只看 `updated_at` 在 `windowMs` 内的 PR；issue 只看 `created_at` 在窗口内的新 Issue；窗口默认 7 天，`0` 表示不过滤。
- issue 流最多查 `maxRepos` 个仓库；每个仓库一次 search，`maxPages` 默认 3，`maxResults` 默认 100。
- `emit` 返回 `accepted: false` 时不写 `seen`；`duplicate: true` 时写 `seen` 并计 duplicate。
- 单流失败时指数退避（从配置周期开始翻倍，最多 30 分钟）；限流时至少等到 `X-RateLimit-Reset`；成功后重置退避。
- 上一轮未结束时跳过本轮，避免子进程与 API 调用堆叠。

## 代价

- 三路顺序执行，单轮耗时是三者之和；量级在数百毫秒到数秒。
- 退避期间面板的「下一轮」会晚于配置周期。
- `windowMs = 0` 时首次安装可能拉取大量历史数据，只靠 `maxResults` 截断。
