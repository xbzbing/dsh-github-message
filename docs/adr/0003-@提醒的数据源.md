# ADR-0003：@ 提醒优先 Notifications，缺 scope 时降级 search

mention 流默认读取 GitHub Notifications 中 `reason=mention|team_mention` 的线程，精确到评论；当 token 缺少 `notifications` scope（且没有 `repo`）时，降级为 `search mentions:@me`。

## 背景

search 只能搜到 Issue/PR，无法直接给出「哪条评论 @ 了我」；Notifications 带 `latest_comment_url`，能定位到具体评论并读取正文。但 Notifications 对公开仓库可能需要 `notifications` scope，而 search 的 `mentions:@me` 只需普通读权限。主人的 `gh` token 当前含 `repo`，Notifications 可用。

## 决策

- 默认 `mentionMode: notifications`。
- 只处理 `reason` 为 `mention` / `team_mention`、`subject.type` 为 `Issue` / `PullRequest` 的通知。
- 用 `latest_comment_url` 读评论；没有评论 URL 时读 Issue/PR 正文。
- 正文必须真的包含 `@<当前账号>`（团队 @ 接受任意 `@slug`）才产出候选，避免把普通订阅通知当 AT。
- `since` 使用上次成功轮询时间减 10 分钟重叠；Notifications 支持 ETag，304 视为无变化；`X-Poll-Interval` 大于配置周期时以 GitHub 为准。
- `mentionMode: search` 作为降级：先看 Issue 正文，正文没有 @ 时读最近 100 条评论；事件粒度到评论，但只保证 Issue 级精确。
- `mentionMode: off` 完全关闭 mention 流。

## 代价

- Notifications 的 `since` 与 read 状态可能带来遗漏；10 分钟重叠与本地 `seen` 兜底。
- 团队 @ 无法验证当前用户是否真在团队里，可能多报；核心可按团队成员再收紧。
- search 降级的评论列表读取有额外请求，且对很长的评论线程只覆盖最近 100 条。
